## 第 1 章 这个产品到底是什么

**一句话**：GCFeed 是一个短视频应用（类似抖音/B站的基础版本）。用户能注册登录、上传视频、发布作品、刷视频流、点赞收藏评论、关注别人。

### 三个部分各是什么

用开店打比方：

| 部分 | 类比 | 技术名 | 代码在哪 |
| --- | --- | --- | --- |
| 网页界面 | 店面。顾客看到的、点的按钮 | React 前端 | `web/src/App.jsx` |
| 后端服务 | 后厨 + 前台接待。所有规矩、所有操作都在这 | Go + Gin | `internal/` |
| 数据库 | 账本。所有数据记在这 | PostgreSQL | `internal/infrastructure/persistence/` |
| 文件目录 | 仓库。视频封面这些大文件放这 | 本地 `uploads/` 目录 | `internal/handler/upload/` |

**一个重要的认知**：网页本身什么都不会。你在页面上点"点赞"，其实是网页向后端发了一条消息（"用户 A 给视频 B 点赞"），真正的判断和记录全是后端做的。网页只是个遥控器。

### 用户能做的六件事

1. **注册 / 登录** —— 拿到一张"通行证"（token）
2. **上传视频** —— 把视频文件、封面图片传到服务器
3. **发布作品** —— 填标题、简介，把上传好的文件路径登记成一条视频记录
4. **刷 Feed** —— 上下滑动看视频流，有两种看法：时间线（最新）和热榜（最热）
5. **互动** —— 点赞、收藏、评论
6. **关注** —— 关注/取关别人，看自己的关注列表和粉丝列表，看自己和别人的主页

## 第 3 章 身份与登录：那张"通行证"是怎么运作的

### 3.1 为什么不能每次都发账号密码

如果用户每点一次赞都要把账号密码发一遍，那么：密码在网络上来回传输的次数越多，被截获的机会越大；而且每次都要查数据库核对密码，很慢。

所以登录一次，服务器发一张**通行证**（token），之后每次请求都带上这张通行证。

### 3.2 这张通行证（JWT）特殊在哪

普通做法是：服务器发一个随机编号，同时在自己数据库里记一笔"编号 X 属于用户 A"。查的时候要查库。

JWT 的做法是：**不记**。通行证本身携带信息，并且带一个**防伪印章**。

JWT 长这样（三段，用点分隔）：`头部.内容.签名`

- **内容**里写着：这是哪个用户（`uid`）、什么角色（`role`）、什么时候过期（`exp`）
- **签名**是用服务器的一把密钥算出来的。别人改了内容，签名就对不上，服务器立刻发现 → 所以内容可以公开，不能伪造

代码位置：`internal/auth/jwt/jwt.go`、`internal/auth/jwt/claims.go`

好处：服务器不用存、不用查库，天然适合很多台服务器一起工作。

### 3.3 几个关键的数字和规矩，分别在防什么

| 规矩 | 代码位置 | 在防什么事故 |
| --- | --- | --- |
| 密钥必须 ≥ 32 字节 | `jwt.go:32`、`config/validate.go:99` | 密钥太短能被暴力猜出来。**一旦猜出，任何人都能伪造任意用户的通行证，等于系统全裸** |
| 通行证 15 分钟过期 | `configs/config.yaml:22` | 万一通行证被偷，小偷也只有 15 分钟的窗口 |
| 必须校验签名算法是 HS256 | `jwt.go:89` | 有一种历史攻击叫"算法混淆"：攻击者把算法改成"不签名"，有些实现就真不验签了。写死算法直接堵死 |
| 必须有过期时间 | `jwt.go:97-99` | 没有过期时间的通行证是永久的，被偷一次永久有效 |
| 必须校验令牌"类型" | `jwt.go:101-103` | 项目里有两种令牌（access / refresh）。如果不校验类型，就能拿长期票当短期票用，绕过短期限制 |
| 密码用 bcrypt 单向加密后才存 | `domain/user/user.go:46` | 数据库万一被脱库，攻击者拿到的是哈希值而不是原密码。bcrypt 还故意算得慢，让暴力破解成本极高 |

### 3.4 两个"预留了但没接线"的东西（重要）

这两个是你以后一定会困惑的地方，也是面试的潜在坑，**必须提前知道**：

**（1）refresh token 是个半成品**

项目里有 `SignRefreshToken` 函数（签发长期票）、有 `TokenTypeRefresh` 类型、有 `refresh_ttl: 168h`（7 天）的配置，还有对应的单元测试（`jwt_test.go:31`）。

但是：**全项目没有任何一处业务代码调用它**，OpenAPI 里也没有"刷新令牌"接口。登录接口返回的响应里只有 `access_token`，没有 `refresh_token`。

所以 `refresh_ttl` 这个配置项目前对运行中的系统**毫无作用**（除了让启动校验通过）。

> **它的本意**：短期票 15 分钟太短，用户用着用着就得重新登录。正确做法是再发一张 7 天的"长期票"，短期票过期后拿长期票去换新的短期票，用户无感。这套机制叫"令牌续期"。
>
> **现状**：设计画了一半，线没接上。面试被问"你怎么处理 token 过期"，**不要假装有**，就说："设计了 refresh 机制，但当前没接通，是个已知缺口，接的时候需要一个 `/api/sessions/refresh` 接口 + 一个 refresh token 的存储或校验。"

**（2）退出登录其实是"假"的**

`DELETE /api/sessions/current` 的实现只有一行：返回 204 什么都不做（`internal/handler/user/handler.go:99-102`）。

原因是：JWT 是"不记名"的，服务器根本没存这张通行证，所以**没有东西可以作废**。真正的"退出"是浏览器把本地存的 token 删掉。

> **这是个真实的安全弱点**：用户点了退出，但那张通行证在 15 分钟内**依然有效**。如果有人已经复制了它，退出登录拦不住他。
>
> **正确做法**：需要一个"黑名单"（把这批还没过期的通行证记下来，每次请求查一下），或者给用户加一个"通行证版本号"，改密码/退出时把版本号加一，旧票全部失效。这两种做法都需要 Redis —— 项目配置里已经有 Redis 段落了（见第 8 章）。
>
> **面试时这是加分项**，主动说出来："无状态 JWT 的退出登录是个经典问题，当前实现只做了客户端删除，服务端没有失效能力，我清楚这个缺口和两种补法。"

### 3.5 一个聪明的设计：Feed 接口是"可选登录"

时间线和热榜允许匿名访问；关注流和推荐流要求登录，并使用 JWT 中的用户身份。

实现方式：`NewOptionalJWTAuth`（`internal/middleware/jwt_auth.go:73-99`）—— 没带通行证就放过去，带了就解析出身份。**注意它和"强制登录"的区别**：强制版没带通行证直接 401 拦掉；可选版一律放行。

代码里还特意做了保护（`jwt_auth.go:75-77`）：如果认证服务根本没初始化（比如配置错了），可选版直接放行，而不是崩掉 —— 因为刷视频流这种核心功能不该被一个配置问题拖死。

## 第 4 章 刷视频流（Feed）：这里面有三个好设计

### 4.1 两种刷法

网页上 Feed 页有两个标签页（`App.jsx:7-10`）：

| 场景 | 含义 | 后端策略 |
| --- | --- | --- |
| `timeline`（时间线） | 按发布时间，最新的在前 | `TimelineStrategy` |
| `hot`（热榜） | 按热度分，最热的在前 | `HotStrategy` |

### 4.2 热度分公式：为什么评论权重最高

```
热度 = 点赞数 × 3 + 评论数 × 5 + 收藏数 × 4
```

代码位置：`internal/domain/feed/feed.go:83-84`

**为什么不是直接按点赞数排？**

因为不同动作的"成本"不一样，成本越高说明用户越真心：

- **点赞**（×3）：抬手一下就完事，最廉价，也最容易被刷
- **收藏**（×4）：用户在想"这个我以后还要再看"，有明确的留存意图
- **评论**（×5）：要打字、要动脑子，成本最高，是真实参与度的最强信号

**面试可能会问**："为什么是 3、5、4 而不是别的数？" 诚实答案：这是拍的经验值，不是算出来的。真正上线要拿数据调参（A/B 测试），这三个数应该做成可配置的。**能说出"这是拍脑袋的、应该做成配置项"比假装它是科学计算要好得多。**

### 4.3 翻页为什么不用"第几页"，而用"书签"

这是整个项目里最值得讲的一个设计。

**普通翻页（页码 / offset）的做法**：`跳过前 20 条，取 20 条`。

两个致命问题：

1. **越翻越慢**：翻到第 100 页，数据库得先把前 1980 条找出来数一遍再扔掉。翻得越深越慢。
2. **内容会错位**：你正在看第 1 页，这时有人发了 3 条新视频。你点第 2 页，数据库是"跳过前 20 条"—— 但因为前面多了 3 条，你**会重复看到刚才看过的 3 条**。反过来如果有人删了视频，你**会漏掉几条**。

**游标翻页（cursor）的做法**：不记"第几页"，记**"我上次看到的那一条排在哪"** —— 像一个书签。下次从书签的位置往后取。

- 不管翻多深，速度一样快
- 有新内容进来也不会错位（书签指向的是内容本身，不是序号）

**这个项目里的书签长什么样**（`internal/application/feed/service.go:267-280`）：

书签 = 把 `{发布时间, 视频ID}` 两个数字打包成 JSON，再 Base64 编码成一串字符返回给前端。前端下次请求原样带回来。

**为什么要带上"视频ID"？** 这是个精妙的细节。如果只用发布时间，而同一秒内发布了 3 条视频，那么"从某个时间点之后取"就分不清这 3 条里哪条已经看过了 —— 会重复或漏掉。**加上视频ID，排序就变成唯一的、稳定的**，边界永远不会错。

这就是为什么代码里排序永远是"时间倒序 + ID 倒序"两个字段（见 `docs/standard.md:284` 的规范）。

**同样的机制用在了三个地方**：时间线 Feed、热榜 Feed、评论列表。各自的书签字段不同：
- 时间线：`{发布时间, 视频ID}`
- 热榜：`{热度分, 发布时间, 视频ID}` —— 热度分会变，所以必须把三个字段都带上才能定位
- 评论：`{评论时间, 评论ID}`

### 4.4 三个防事故的小规矩

| 规矩 | 代码位置 | 在防什么 |
| --- | --- | --- |
| 一次最多返回 100 条 | `domain/feed/feed.go:8`、`service.go:197-199` | 如果有人手动传 `limit=999999`，数据库要一次捞出全表，服务直接被拖死。超过 100 就悄悄按 100 处理 |
| 一次多取 1 条来判断有没有下一页 | `service.go:164,170` | 想判断"后面还有没有数据"，笨办法是再查一次总数。多取 1 条，如果拿到了 11 条（要 10 条），说明还有下一页。**省掉一次数据库查询** |
| 不合法/被篡改的书签直接报错 | `service.go:224-226` | 书签是前端传回来的，用户可以随便改。解出来不像话就报错，不能让脏数据进到 SQL 里 |

> 顺带一提：`service.go:210-216` 那个书签解码，先试 URL 安全编码、失败再试标准编码 —— 这是为了兼容前端可能传回来的两种编码格式，属于**宽容解析**，对调试友好。

### 4.5 场景用"策略模式"：为的是以后加推荐流不用改调用方

`scene` 参数进来后，服务不是写一堆 `if scene == "timeline" ... else if scene == "hot"`，而是查一张**注册表**（`internal/application/feed/service.go:17,37-38,64-67`）：场景名 → 对应的处理策略。

好处：将来要加"推荐流"，只需要新写一个策略并在启动时注册一下，**已经写好的代码一行都不用改**。

当前已注册 timeline、hot、following 和 recommend 四个策略；推荐流复用现有查询入口和卡片组装。

推荐排序、曝光过滤和边界说明见 [推荐模块](modules/recommendation.md)。

## 第 5 章 为什么点赞需要一个"幂等键"

### 5.1 先讲事故

用户在地铁里点了一下赞。网络很卡，手机没收到响应，于是**自动重发了一次**。服务器收到了两条一模一样的"点赞"请求。

如果没有防备：第一条让点赞数变成 10，第二条又变成 11。用户只点了一下，数字却涨了两下。

另一种情况更常见：用户手快连点两下，或者用户以为没点上又补了一下。

**幂等**就是解决这个的：**同一个请求做多少次，结果都跟做一次完全一样。**

### 5.2 幂等键是什么

`idempotency_key`（幂等键）= **这次操作的唯一编号**，由客户端生成。

前端生成的样子（`App.jsx:534`）：`web-like-{视频ID}-{当前时间戳}` —— 里面带了时间戳，所以每次操作都是一个新的编号。

服务器看到同一个编号，就知道"**这事我办过了**"，直接把上次的结果还给你，而不是再办一遍。

> 这个字段最反直觉的地方：**它不是给"去重"用的，是给"重放"用的。** 它的价值不在于"拦住第二次"，而在于"第二次也能拿到正确的答案"（比如第一次的响应在网络上丢了，客户端重试，得能拿回同样的结果）。

### 5.3 三层防线（设计得相当讲究）

这个项目用了三道防线，一层比一层可靠：

**第一层：先查"收据"**（`application/interaction/service.go:64-75`）
请求进来先查有没有这个幂等键的记录，有就直接返回上次的结果。

**第二层：数据库里的"收据表"**（`persistence/interaction/repository.go:70-90`）
正式开工前，在事务里用 `FOR UPDATE` 锁着查一次收据表。查到就直接返回快照，**完全不动统计数据**。

**第三层：唯一索引兜底**（`model.go:25-27` 的 `uk_user_action_idempotency`）
如果两个一模一样的请求**同时**到达，它们会同时查不到收据、同时开工。这时候唯一索引发威：两个都想往收据表里插同一条记录，数据库只让一个成功，另一个直接报"唯一键冲突"。

**最精妙的是这个报错之后发生了什么**（`repository.go:141-154`）：

1. 插入收据这一步，是放在**事务的最后**做的
2. 插入失败 → 整个事务**回滚** → 前面偷偷加掉的那个点赞数**被撤销了**
3. 然后代码抓住这个"唯一键冲突"，转头去读那个抢先者的结果，返回给用户

**结果：两个并发请求，点赞数只加了一次，两边都拿到了正确的结果。** 这是"乐观锁 + 唯一索引"的经典用法，设计是对的，值得在面试里讲。

### 5.4 为什么全程用事务和"锁行"

`SetAction` 全部包在一个事务里，而且反复出现 `clause.Locking{Strength: "UPDATE"}`（这就是 SQL 里的 `SELECT ... FOR UPDATE`，意思是"这行我锁了，别人等着"）。

防的是什么？假设两个用户同时给同一个视频点赞，两个人同时读到"当前 10 个赞"，各自加一，各自写回 11 —— **两个赞变成了一个**。这叫"丢失更新"。加锁之后，第二个人必须等第一个人写完，读到的是 11，再加一得到 12。

代码里锁了三样东西：
- 视频行（`lockPublishedVideo`）：确认视频存在且已发布，防止给已删除的视频点赞
- 动作行：防止同一个用户并发点赞产生两行记录
- 统计行（`updateVideoStatCounter`）：防止计数丢失更新

代价是：同一时刻很多人给同一个热门视频点赞，会排队。这就是为什么第 6 章说计数要单独放一张窄表 —— 锁一行只有三个数字的记录，比锁一整行视频记录便宜。

### 5.5 计数为什么"先读出来加一，再写回去"

看 `updateVideoStatCounter`（`repository.go:461-482`）：它把整行读出来、在内存里加 delta、再 `Save` 写回整行。

这**不是**最高效的写法。更快的做法是发一条 `UPDATE video_stat SET like_count = like_count + 1`，让数据库自己加，不需要先读。

代价对比：
- 现在的写法：先读一次、再写一次（两次往返），但因为是"先锁行再读"，所以**是安全的**
- 更快的写法：一次往返、天然原子，但**拿不到更新后的值**，想返回新数字还得再查一次

作者选了前者，换来了"一次交互只查一轮就能返回最新数字"。在这个规模下是合理的取舍。**面试被问到"高并发下这样会不会慢"，可以答：会，瓶颈是行锁排队；解法是改成原子自增 + Redis 计数，代价是返回值要另想办法。**

### 5.6 ⚠️ 我在点赞逻辑里发现了一个真实的 Bug

**这一节请务必看完，这是本文档最重要的发现。**

#### 现象

`PUT /api/videos/{id}/like`（点赞）和 `DELETE /api/videos/{id}/like`（取消点赞）本该是"设置状态"：PUT 把它设成"已赞"，DELETE 把它设成"未赞"。

但仓储层的实际写法（`persistence/interaction/repository.go:103-127`）是这样：

```go
delta := 1
nextStatus := actionStatusFromActive(active)
...
if action.Status == nextStatus {          // 已经是想要的状态了
    action.Status = ActionStatusCanceled  // 反而把它取消掉
    delta = -1
} else {
    action.Status = ActionStatusActive    // 无条件设成"已赞"
}
```

这段代码的逻辑是**"翻转"（toggle）**，而不是"设置"。而且 `else` 分支硬编码成 `Active`，**完全忽略了请求到底想要什么状态**。

#### 逐个情况推演

把前端的行为代进去（前端是标准的设置语义：想赞就 PUT，想取消就 DELETE，见 `App.jsx:527-531`）：

| 你的操作 | 期望 | 实际发生 | 对不对 |
| --- | --- | --- | --- |
| 第一次点赞 | 变成已赞，+1 | 新建一行"已赞"，+1 | ✅ 对 |
| 取消点赞 | 变成未赞，−1 | **仍然是已赞，而且 +1** | ❌ **错** |
| 已经赞过，再点一次赞 | 保持已赞（无变化） | **变成未赞** | ❌ **错** |
| 没赞过，直接取消点赞 | 保持未赞（无变化） | **变成已赞，而且 +1** | ❌ **错** |

**后果**：用户点"取消点赞"时，爱心不会熄灭，点赞数反而会 +1。收藏（favorite）走的是同一段代码，有同样的问题。

#### 为什么这个 Bug 能活到现在

看仓储层的测试文件（`persistence/interaction/repository_test.go`），它只测了四种情况：空仓储报错、非法参数报错、幂等快照能正确返回、评论字数按字符算。

**没有任何一个测试覆盖"点赞和取消点赞的状态转换"。** 这是一个关键逻辑，却完全没有测试保护 —— 这也是为什么它能一直藏着。

> **这件事本身就是最好的面试素材**：它证明了"测试覆盖率"这个词不是空的。这个 Bug 之所以存在，就是因为"最该测的那条路径"没测。

#### 怎么修

正确逻辑应该是"按请求设置状态"，并且只在状态**真的发生变化**时才动计数：

```
如果请求是"点赞"：
    如果已经是已赞 → 什么都不做（幂等），返回当前计数
    否则 → 设为已赞，计数 +1
如果请求是"取消点赞"：
    如果已经是未赞 → 什么都不做（幂等），返回当前计数
    否则 → 设为未赞，计数 -1
如果这行记录根本不存在：
    点赞 → 新建"已赞"行，计数 +1
    取消点赞 → 什么都不做（或者建一行"未赞"），计数不变  ← 现在的代码在这里写死了"已赞 +1"，是错的
```

**这件事值得做**：修好它 + 补一个覆盖四种情况的测试。修完之后，你就有了一个"我发现并修复了一个并发/状态机的真实缺陷"的故事，**这比多写三个新功能更能打动面试官。**

### 5.7 其他几个"防事故"的细节

| 设计 | 代码位置 | 在防什么 |
| --- | --- | --- |
| 评论最多 1000 个**字符**（不是字节） | `domain/interaction/interaction.go:19,79` | 用的是 `utf8.RuneCountInString` 而不是 `len()`。因为一个汉字在 UTF-8 里占 3 个字节，如果按字节算，**333 个汉字就被判成超长了** —— 中文用户会觉得莫名其妙。标题的 128 字限制同理（`domain/video/video.go:53`） |
| 取关不删记录，只改状态为 2 | `domain/relation/relation.go:9-10` | 保留历史：能查出"他曾经关注过我又取关了"，也避免了反复插删导致的自增 ID 疯涨。点赞、评论同样用状态位而不是物理删除 |
| 幂等键最多 128 字节 | 各 domain 文件 | 防止有人往这个字段里塞一大段数据 |
| 计数在减的时候不允许低于 0 | `repository.go:508-513` 的 `clampCount` | 兜底。万一出现"取消点赞"多于"点赞"的异常情况（比如重复提交），数字至少不会变成 −5 这种一看就是坏掉的样子 |

### 6.2 三个最重要的设计决定

#### 决定一：为什么点赞数不直接放在 `videos` 表里

这是面试**极有可能被问到**的一题。

`videos` 表存的是作品的"档案"（标题、地址、作者）；`video_stat` 表专门存三个计数（`model.go:26-33`）。

**为什么不合并成一张表？**

1. **读写冲突**。刷 Feed 时要读 `videos` 表（拿标题、封面）；而每有一个点赞就要写 `videos` 表。**读得最频繁的行，恰好也是写得最频繁的行**，两边的锁会互相排队。
2. **锁的代价**。点赞要在事务里锁住统计行。锁一行"只有三个数字"的窄记录，比锁一整行带标题、简介、URL 的宽记录便宜得多。
3. **缓存友好**。作品的档案内容基本不变（改标题很少见），适合长期缓存；计数每秒都在变。拆开之后可以**只缓存档案，不去碰计数**。

**代价是什么？** 每次查 Feed 都得多 JOIN 一张表（`feed/repository.go:162`），而且可能出现"视频有了但统计行还没建"的尴尬。

**项目怎么兜这个底？** 有两道保障：
- 发布视频时在同一个事务里连统计行一起建（`video/repository.go:66` 的注释）
- 启动时跑一次 `EnsureStats`（`video/repository.go:42-64`）：用一条 SQL 把所有"没有统计记录的已发布视频"补上统计行，用的是 `INSERT ... SELECT ... LEFT JOIN ... WHERE vs.video_id IS NULL ON CONFLICT DO NOTHING`

> `EnsureStats` 还藏着一个历史信息：它会检查 `videos` 表里**是否还有旧的计数字段**（`like_count` 等），如果有，就把旧值搬进新表。**这说明计数原本就在 `videos` 表里，是后来拆出去的**，而这个函数就是那次拆分的迁移工具。这就是"为什么会有这个函数"的答案。

#### 决定二：为什么 `idempotency_key` 字段是"可空"的（`*string` 而不是 `string`）

这个细节非常精妙，**是"为什么要有个奇怪的类型"的完美例子**。

看 `interaction_comment` 表的索引定义（`model.go:44,47`）：

```
uk_user_idempotency = (user_id, idempotency_key)   ← 唯一索引
```

意思是"同一个用户的同一个幂等键，只能出现一次"。这是幂等的最后防线。

**问题来了**：幂等键是**可选的**。如果客户端没传，这个字段就是空的。如果它是 `string` 类型、空值存成空字符串 `''`，那么：

> 用户 A 发的**第二条**不带幂等键的评论，会撞上第一条的空字符串 → **唯一索引报错 → 评论发不出去。**

也就是说，用户这辈子只能发一条不带幂等键的评论。

**解法**：让这个字段可空（存 `NULL`）。因为 **SQL 的唯一索引不把 `NULL` 当回事**（多个 `NULL` 之间不算重复）。这样 "有键的" 走唯一约束、"没键的" 互不干扰。

代码里专门有个小函数干这件事（`video/repository.go:320-326`）：

```go
// idempotencyKeyPtr 将空幂等键转换为 nil，避免占用唯一约束。
func idempotencyKeyPtr(value string) *string {
    if value == "" {
        return nil   // 空字符串 → NULL
    }
    return &value
}
```

**"因为唯一约束不认 NULL，所以空值必须转成 NULL 而不是空字符串"** —— 这个知识点很实用，面试说出来会让人眼前一亮。

#### 决定三：`user_follow_idempotency` 表为什么那么"胖"

对比一下两张收据表：

- `interaction_action_idempotency` 只存了 8 个字段，其中包含点赞数、收藏数
- `user_follow_idempotency` 存了 **17 个字段**（`relation/model.go:22-40`），包括：关注关系本身的创建/更新时间、**发起方的关注数和粉丝数**、**被关注方的关注数和粉丝数**，以及这四条统计各自的创建/更新时间

**为什么关注需要存这么多？**

因为两个动作的影响范围不一样：
- 点赞只影响**一个视频**的计数（存两个数字就够）
- 关注同时影响**两个人**：我的"关注数"+1，对方的"粉丝数"+1

幂等的意义是"重试时**原样**返回上次的结果"。既然一次关注动了两个人的四个数字外加两条时间戳，收据里就必须把这一整套结果都记下来，重试时才能一模一样地还回去。

**这是"收据要记全"这个原则的直接体现** —— 记录的成本，换来的是重试结果的完全一致。

### 6.3 索引：为哪条查询而生

数据库索引就像书末尾的索引页：**没有它，每次查询都要从头翻到尾。**

这个项目的大多数索引，都是**照着某一条具体查询量身定做的**。看懂这个对应关系，你就看懂了索引存在的意义：

| 索引 | 定义在哪 | 支撑哪条查询 | 没有会怎样 |
| --- | --- | --- | --- |
| `idx_video_timeline` | `video/model.go:7,13,14` | `WHERE status=已发布 AND published_at IS NOT NULL ORDER BY published_at DESC, id DESC`（`feed/repository.go:163,82-83`） | 时间线是首页主路径，每次刷新都要把全表排序一遍，**用户越多越慢** |
| `idx_author_status` | `video/model.go:8,13,16` | 看某人的作品列表（按作者 + 状态过滤） | 看别人主页会全表扫描 |
| `uk_author_idempotency` | `video/model.go:8,15` | 防止同一个发布请求重试产生两条视频 | 用户手抖会发出两条重复作品 |
| `uk_user_video_type` | `interaction/model.go:8-10` | 保证"一个用户对一个视频的一种动作**只有一行**" | **这是整个点赞设计的基石**。因为只有一行，才能靠"改这一行的状态"来表示赞/取消赞；否则会出现两行记录，不知道听谁的 |
| `uk_user_idempotency`（评论表） | `interaction/model.go:44,47` | 评论幂等的最后防线 | 重试会发出重复评论 |
| `idx_video_status_created` | `interaction/model.go:43,46,48,49` | 按时间倒序翻某个视频的正常评论（`WHERE video_id=? AND status=正常 ORDER BY created_at DESC, id DESC`） | 看评论列表会全表扫评论表 |
| `uk_user_target` | `relation/model.go:8-9` | 保证一对用户之间只有一条关注关系 | 反复关注/取关会堆积重复行，粉丝数就会算错 |
| `idx_user_status_updated` / `idx_target_status_updated` | `relation/model.go:8-13` | 分别支撑"我的关注列表"和"我的粉丝列表" | 关注/粉丝列表全表扫描。**注意这两个索引是分开的两条**，因为同一张表要支持两个方向的查询 |

### 6.4 一个"索引救不了"的地方：热榜查询

热榜的排序依据是**临时算出来的热度分**（`feed/repository.go:14`）：

```sql
COALESCE(vs.like_count,0)*3 + COALESCE(vs.comment_count,0)*5 + COALESCE(vs.favorite_count,0)*4
```

然后 `ORDER BY hot_score DESC, published_at DESC, id DESC`（`:144-146`）。

**问题**：这个 `hot_score` 不是表里的一个列，而是每次查询现算的表达式。**数据库无法为"计算结果"建索引**，所以这条查询只能：把已发布的视频全捞出来 → 逐行算分 → 排序 → 取前 10 条。

而且游标翻页的 `WHERE` 条件里，这个表达式还被重复写了 3 遍（`:133`），计算量再翻三倍。

**这意味着什么？**
- 视频总量小（几千条）时，完全没问题
- 视频量大了以后，**热榜会成为最慢的接口**，而且翻到第几页都一样慢

**正确解法**（面试可以主动说）：
- 把 `hot_score` 做成 `videos` 表里的一个**真实列**，定期（比如每分钟）由一个后台任务重算并写回，然后给它建索引
- 或者把热榜结果放进 Redis 的**有序集合**（ZSET），定时刷新 —— 这正是项目配置里那个"预留的 Redis"将来该干的事（见 `docs/optimization.md`）

### 6.5 "状态"字段：为什么到处是 1、2、3、4

你在表里会看到大量 `status int`。它们的含义**每张表都不一样**，这是最容易看晕的地方，这里一次性列清楚：

| 表 | 值 | 含义 |
| --- | --- | --- |
| `users` | 1 | 正常（`domain/user/user.go:12`） |
| `videos` | 1 / 2 / 3 / 4 | 草稿 / **已发布** / 已下架 / 已删除（`domain/video/video.go:10-13`） |
| `interaction_action` | 1 / 2 | 生效（已赞/已收藏）/ 已取消（`domain/interaction/interaction.go:13-14`） |
| `interaction_comment` | 1 / 2 | 正常 / 已删除（`:16-17`） |
| `user_follow` | 1 / 2 | 关注中 / 已取关（`domain/relation/relation.go:9-10`） |

**为什么要用数字而不是"已删除"这样的文字？**
- 数字占空间小、比较快、能建索引（这是主要理由）
- 代价是**可读性差** —— 所以你看到代码里到处是 `StatusPublished` 这样的常量，那就是在给数字起名字

**为什么删除是"改状态"而不是真删？**
1. 数据还能救回来（误删能恢复）
2. 保留历史（谁什么时候取关了谁）
3. 关联数据不会变成孤儿（评论还挂在视频上，只是视频不再展示）

**代价**：所有查询都必须记得带上 `status = 已发布` 这个条件。**一旦漏写，删掉的视频就会重新出现在首页上。** 项目里的做法是把这个条件统一放在 `baseFeedQuery`（`feed/repository.go:157-164`）和各个仓储方法里，避免每个地方手写。

## 第 7 章 代码为什么要分成四层

你翻代码时会发现目录是这样的：`internal/handler/`、`internal/application/`、`internal/domain/`、`internal/infrastructure/`。**为什么要这么麻烦，不能全写一个文件里？**

用一家餐厅打比方：

| 层 | 类比 | 代码位置 | 只负责 |
| --- | --- | --- | --- |
| Handler（接口层） | 前台接待 | `internal/handler/` | 收客人说的话、转成内部格式、把结果包装成 HTTP 响应 |
| Application（应用层） | 值班经理 | `internal/application/` | 编排一个完整用例的步骤：先校验、再查、再写、再算下一页 |
| Domain（领域层） | 规矩手册 | `internal/domain/` | 纯业务规则：标题不能为空、不能关注自己、热度怎么算 |
| Infrastructure（基础设施层） | 仓库管理员 | `internal/infrastructure/` | 只管和数据库打交道，把数据存进去/取出来 |

### 为什么值得这么分

1. **改数据库不用动业务规则**。哪天从 PostgreSQL 换成别的数据库，只需要重写 `infrastructure/`，`domain/` 里的规矩一个字都不用改。
2. **业务规则可以单独测试**。项目的 `_test.go` 测试文件有 20 多个，`domain/` 和 `application/` 的测试不需要真的连数据库就能跑 —— 这就是**为什么 `go test ./...` 能全部通过**。如果全写在一起，每个测试都得先装一个数据库。
3. **依赖方向是单向的**：外面依赖里面，里面不认识外面。所以你会发现 `internal/domain/` 里的文件**没有一行 import gin 或 gorm** —— 这是刻意的，领域规则不该知道"自己是通过网页还是别的什么被调用的"。

> **面试可能问**："分层会不会让代码变啰嗦？" 诚实答案：会。一个小功能要在四个文件里各写一点。项目现在这个规模，收益（可测试、可替换）大于成本。但如果只是个小工具，这么分就是过度设计。

### 启动顺序（`cmd/server/main.go`）

程序启动只做四件事，顺序不能乱：

1. 读配置（`configs/config.yaml` + 环境变量）
2. 连数据库（连不上就直接退出，不要带病运行）
3. 建表 / 补字段（`router/register.go:45-62` 的 `AutoMigrate`）
4. 注册路由、启动服务

第 3 步值得多说一句：项目用的是 GORM 的**自动建表** —— 代码里的结构体定义长什么样，数据库的表就长什么样，程序启动时自动对齐。好处是开发快；**代价是生产环境不该这么干**（改字段可能锁表、可能丢数据），正规做法是用迁移脚本。这一点面试被问到要主动承认。

## 第 9 章 面试问答速查

### 基础问题

**Q：介绍一下这个项目。**
这是一个短视频 Feed 系统的后端服务，用 Go + Gin 写的，数据库是 PostgreSQL，前端是 React。核心功能是用户体系、视频发布、Feed 流、互动（点赞收藏评论）和关注关系。代码按接口层、应用层、领域层、基础设施层分成四层，共 9 张数据表、26 个测试文件。

**Q：为什么选 Go？**
（如果你自己决定的，就说理由：）Go 编译成单个可执行文件、部署简单，标准库自带 HTTP 服务，并发模型适合这种 IO 密集的 Web 服务，而且 Gin 生态成熟。
（如果说不清，就诚实说"这是我练手的选型，看中的是部署简单和社区教程多"。）

**Q：数据库为什么用 PostgreSQL？**
注意：**别说 MySQL**（见 8.1）。说 PostgreSQL，理由是功能完整、GORM 支持好、JSON 字段和索引能力强。如果被问"为什么不用 MySQL"，可以说"对这个规模两者都够用，选 PostgreSQL 是个人偏好/教程顺手"。

### 核心设计问题（这几题一定要会）

**Q：Feed 翻页怎么实现的？为什么不用 offset？**
游标分页。游标里存的是上一页最后一条的排序字段（时间 + ID），Base64 编码后返回给前端。不用 offset 有两个原因：一是翻得越深数据库扫描越多越慢；二是 offset 在数据插入/删除时会错位，导致重复或漏掉内容。带上 ID 是为了让排序唯一稳定，避免同一时间戳的边界问题。

**Q：为什么要 limit + 1？**
为了判断"还有没有下一页"而不需要额外查一次总数。多取一条，取到了就说明后面还有。

**Q：点赞怎么防止重复？**
用幂等键。客户端为每次操作生成一个唯一编号（idempotency_key），服务器看到同一个编号就知道这个操作已经处理过，直接返回上次的结果而不是再加一次。防的是网络重试、用户连点两下这类情况。

**Q：计数（点赞数）会不会有并发问题？**
会，防了。整个互动操作包在数据库事务里，并且用 `SELECT ... FOR UPDATE` 依次锁住视频行、动作行、统计行。防的是"丢失更新"：两个人同时读到 10，各自加一写回 11，两个赞变成一个。加锁后第二个人必须等前一个人提交，读到 11 再加一得到 12。

代价是热门视频的点赞会排队。再往上优化就是改成 `UPDATE ... SET like_count = like_count + 1` 让数据库原子自增，或者用 Redis 计数异步落库 —— 但那样就拿不到"更新后的准确值"直接返回了，需要另外想办法（比如返回后由前端再拉一次）。

**Q：这个项目里你觉得最值得改进的地方是什么？**（很常见的开放题）
（按这个顺序说，显得你既懂业务又诚实：）
1. **互动状态机有缺陷**：取消点赞的计数方向反了，而且这块最关键的逻辑没有测试覆盖 —— 我已经定位到 `repository.go` 的状态转换分支
2. **热榜查询走不了索引**：热度分是查询时现算的表达式，没法建索引，数据量上来一定会慢；应该把热度分做成真实列定期重算，或者放 Redis 的有序集合
3. **退出登录服务端无失效能力**：这是无状态 JWT 的固有代价，需要黑名单或版本号来补
4. **refresh token 只写了一半**：有签发函数和配置，但没有刷新接口
5. **文档和代码不一致**：架构文档写 MySQL，实际是 PostgreSQL；关注模块已经实现但文档还标着"未实现"

**Q：热度分怎么算的？**
点赞×3 + 评论×5 + 收藏×4。权重不同是因为用户成本不同：点赞最廉价、评论成本最高最能代表真实参与。这三个系数是经验值，上线后应该用数据调参，最好做成可配置。

**Q：怎么保证用户只能删自己的视频/评论？**
在领域层校验。`domain/video/video.go:127-138` 的 `DeleteBy` 会比对"视频作者"和"当前请求者"，不一致就返回权限错误。删除用的是软删除（把状态改成"已删除"），保留历史数据。

**Q：JWT 是怎么工作的？退出登录怎么办？**
（照 3.2 和 3.4 说。**退出登录那题一定要主动说出"这是无状态 JWT 的固有难题，当前只做了客户端删除，服务端没有失效能力，正确做法是黑名单或版本号"** —— 这题答好了是加分项。）
