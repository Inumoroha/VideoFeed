## 关键设计

### 用户消息接口与内部鉴权

| 方法 | 路径 | 鉴权与行为 |
| --- | --- | --- |
| GET | `/api/messages` | JWT；按创建时间和 ID 倒序分页，默认 20 条，最多 100 条 |
| GET | `/api/message-stats/unread` | JWT；统计当前用户全部未读消息 |
| PATCH | `/api/messages` | JWT；指定消息去重后标记已读，省略、null 或空 `message_ids` 表示全部已读 |
| POST | `/internal/messages` | `X-Internal-Token`；首次创建返回 201，幂等重放返回原消息和 200 |

用户接口始终以登录身份限定查询和更新范围。已读操作忽略他人或不存在的消息，只更新尚未读的记录；重复操作不会改写原已读时间。

内部创建使用独立令牌中间件，保留去空白和常量时间比较。错误响应适配当前仓库统一的 `error` 字段。配置 `internal.token` 默认为空，未配置时拒绝内部创建；用户查询和业务自动通知不依赖此令牌。既有内部推荐接口的认证行为没有随之改变。

四个实际方法已同步到 [OpenAPI](../../api/openapi.yaml)，包含请求、响应、错误状态和鉴权。消息前端只访问用户接口，不携带内部令牌。

### 消息模型与数据库幂等

PostgreSQL 表 `user_message` 保存收件用户、类型、标题、内容、事件标识、幂等键、已读状态及创建和已读时间。消息类型为 `LIKE`、`COMMENT`、`FOLLOW`、`SYSTEM`，输入去空白后转大写。

| 校验项 | 当前约束 |
| --- | --- |
| 收件用户 ID | 必须为正数，不额外查询用户是否存在 |
| 标题、内容 | 去除首尾空白后非空，分别最多 128、1024 个 UTF-8 字节 |
| 事件标识、幂等键 | 分别最多 64、128 个 UTF-8 字节 |
| 事件唯一性 | `(user_id,event_id)` 唯一 |
| 请求唯一性 | `(user_id,idempotency_key)` 唯一 |

空事件标识和空幂等键以 NULL 保存，因此无键请求可以重复创建。发生唯一冲突时先回滚失败事务，再按同一用户查找既有消息；两个键分别命中不同消息时，保留源实现返回较大 ID 的规则。

仓储补充 PostgreSQL SQLSTATE `23505` 识别，并保留 GORM 和文本兼容识别。索引名称增加消息前缀，避免 PostgreSQL schema 内重名，同时补齐 `(user_id,created_at)` 列表索引。

消息表注册到现有共享迁移流程，继续使用事务级咨询锁 `pg_advisory_xact_lock(736496102)`，保留 API 与 worker 并发启动时的串行迁移、失败回滚和锁释放语义。

### 互动通知与失败边界

```text
点赞、评论或关注请求
  -> 执行原有业务及幂等处理
  -> 满足通知条件（关注还需回填成功）
  -> 消息适配器调用消息服务
  -> 按收件用户和事件键写入或返回既有消息
  -> 用户通过消息页查询并标记已读
```

| 触发条件 | 收件人 | 确定性事件键 |
| --- | --- | --- |
| 有效点赞且实际变化量大于零 | 视频作者，自赞除外 | `interaction:like:<videoID>:<userID>` |
| 真正新增评论 | 视频作者，自评除外 | `interaction:comment:<commentID>` |
| 有效关注且关注流回填成功 | 被关注用户 | `relation:follow:<targetUserID>:<userID>` |

收藏、取消点赞、取关和删除不生成通知。取消后重新点赞或关注仍复用原事件键，同一收件用户最终只有一条对应消息。

互动仓储新增可选扩展 `NotificationRepository`，提供作者查询及 `SetActionWithDelta`、`CreateCommentWithDelta`。生产 GORM 仓储实现扩展，原 `SetAction`、`CreateComment` 的签名、计数快照和状态行为保持兼容；仅实现旧接口的自定义仓储仍可使用，但不具备通知所需信息。

通知属于尽力写入：查询作者或保存通知失败，不改变主业务成功结果。关注回填失败仍返回原错误，客户端重试并成功回填后才尝试通知。异步点赞发布失败时保留同步落库回退，只在保存成功且产生实际变化后通知；保存失败不通知。

本轮保留 Redis WATCH/事务及原子变化量，没有用普通读改写替代并发保护。RabbitMQ 继续使用现有拓扑、互斥发布、手动确认、无效消息拒绝、业务失败重新入队和关闭流程。通知在 API 请求内写数据库，没有新增消息专用队列、消费者、自动重试或补偿任务。

### 前端消息页与请求隔离

`web/src/App.jsx` 增加 `/messages`，桌面顶部铃铛和侧栏均提供入口；访客访问消息页时跳转 `/auth`。移动导航由四个 Feed 入口扩为五项，复用 900px 和 560px 断点。

- 导航角标统计全局未读，超过 99 显示 `99+`；会话、路由变化和成功已读后刷新，没有后台轮询。
- 消息页每次加载 20 条，手动续页并按 ID 去重，提供加载中、空列表、错误重试和刷新状态；续页失败保留已有列表。
- 点击未读消息提交该 ID，全部已读提交空数组；成功后更新可见项并刷新角标，失败保留原状态供重试。
- 页面标题旁的未读数仅统计已加载消息，导航角标统计全部消息，两者可能不同，保留源实现语义。
- 列表和已读操作遇到 401 时清理会话并跳转登录；独立角标请求遇到 401 清零，其他错误保留原数值。

为适配当前 React 结构，导航回调保持稳定，避免角标更新导致消息列表 effect 循环请求。请求版本与会话身份共同隔离旧响应，账号切换或页面卸载后，旧列表、已读错误和角标结果不能覆盖新状态；这是忽略过期结果，不代表取消底层网络请求。

ref 锁即时拦截重复点击，将列表刷新、分页、单条及全部已读串行化，防止旧列表覆盖已读状态，并在完成或失败后释放锁。移动样式只隐藏导航文字，不再把新增角标误当作最后一个文字元素隐藏。

## 当前边界与后续计划

消息存储、业务通知、页面展示及已读操作已经接通，但通知仍是尽力写入。主业务与消息写入不是统一可靠投递事务，通知失败可能丢失；当前没有事件发件箱、重试队列或补偿扫描。确定性事件键还意味着重新点赞、重新关注不会产生第二条对应通知。

内部创建只校验收件用户 ID 为正数，不检查用户存在性；自定义互动仓储需要实现扩展接口才能提供通知。页面未读统计区分已加载数量和全局数量，且没有实时推送或后台轮询。

- 使用专用 PostgreSQL 跑通并发、唯一约束、分页及已读幂等测试，再补真实 API、worker 和浏览器联调。
- 明确通知可靠性目标，设计事件发件箱、失败重试和补偿机制，并增加投递失败观测。
- 明确重复点赞、重复关注及页面未读数量的产品语义，再决定是否调整当前规则。
- 后续接入审核事件通知；增加实时刷新或推送前，先定义频率、鉴权和断线恢复行为。
